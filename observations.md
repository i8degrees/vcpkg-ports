## Security / supply-chain notes

- Both ports use `vcpkg_download_distfile` with SHA512 hashes: good.
- `librocket` zips a tagged release: good.
- `nomlib` zips the `dev` branch: bad. SHA512 will drift whenever the branch moves, breaking reproducible builds.
- The `vcpkg-cmake-wrapper.cmake` in `librocket` uses only installed-directory paths and NO_DEFAULT_PATH; no host escape.
- No obvious network fetching from cmake wrappers or portfiles beyond declared downloads.

## Tooling observations

- `vcpkg print-usage <port>` is **not supported** by the installed vcpkg binary.
- `vcpkg x-ci-verify-versions --x-builtin-ports-root=./ports --x-builtin-registry-versions-dir=./versions` fails because the standalone registry has no default baseline to resolve upstream ports (`freetype`, `vcpkg-cmake`, etc.). This is expected for a custom overlay/registry without a default registry; verification should be run in a consumer project or with `--x-builtin-registry-versions-dir` plus the upstream registry.
- `vcpkg format-manifest ports/librocket/vcpkg.json` and `ports/nomlib/vcpkg.json` were not re-run during this audit; both files already have the schema field and appear well-formed.

## Overall verdict

`librocket` builds and installs on `x64-linux`, but ships Debug artifacts for Release triplets and has several consumer-facing CMake issues.

`nomlib` builds on this machine because the `dev` branch zip was cached, but:
- the branch-head SHA512 has already drifted,
- manifest-mode resolution will fail due to `version>=` scheme conflicts,
- `find_package(nomlib CONFIG REQUIRED)` cannot work because config fixup is disabled,
- the `usage` file is inaccurate.

**Recommended fix order:** fix nomlib sourcing (tag/commit pin) + `version>=` constraints, then librocket Debug override, then the nomlib consumption/usage issues, then registry/version-db hygiene.
